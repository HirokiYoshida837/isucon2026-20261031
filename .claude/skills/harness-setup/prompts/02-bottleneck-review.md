# 02. ボトルネックの洗い出し（視点別・並行）

## いつ・誰が
- 午前: APM 導入後のベンチ直後に 0 → A と B を並行 → E
- 午後: 午前の改善が一段落したら 0 → C と D を並行 → E
- A〜D はコードを変えない。別セッションで同時に走らせ、自分の出力ファイルだけに書く

## 0. 計測スナップショット（1 セッション）
````text
ベンチ直後の計測値を docs/measure/<<HHMM>>/ に保存してほしい。
今回: スコア <<スコア>> / <<PASS か FAIL>> / コミット <<短い hash>> / ベンチ所要 <<分>> 分
- SKILL newrelic-nrql で endpoints / sql / hosts / procs / errors を tsv で保存する（期間はベンチ所要 + 2 分）
- bench-report.sh の添付（alp / pt-query-digest）があれば同じ場所に置く
- summary.md に、上位 5 エンドポイント・上位 5 SQL・サーバー別 CPU・エラー件数を 1 行 1 文で書く
- コードと設定は変えない
````

## A〜D（視点を変えて別セッションで貼る）
````text
ISUCON の改善点を「<<視点（下の表から）>>」の視点で洗い出してほしい。コードは変えない。調査と報告だけ。
読むもの: CLAUDE.md、docs/（regulation / scoring / endpoints / schema）、docs/measure/<<HHMM>>/
書き込みは docs/review/<<A-db など>>.md だけ。

出力形式
- 最初に「結論: 先にやるべき 3 件」を 3 行で書く
- 候補を表にする。1 候補 1 行。列: ID（視点の記号 + 連番）/ 候補 / 対象（ファイル:行 か設定ファイル）/ 根拠の計測値（出典付き。無ければ「コードから推測」）/ 期待効果（大中小 + 理由 1 文）/ リスク（レギュレーション・FAIL の可能性）/ 作業量（S 30 分・M 2 時間・L 半日）/ 時間帯（午前・午後）
- 表の後に上位 3 件だけ、変更の要点・成功の確認方法・戻し方を各 5 行以内で書く
````
| 視点 | 見るもの |
|---|---|
| A. DB クエリ（午前） | 合計時間の大きい SQL の index（EXPLAIN は読み取りで可）、単一テーブルの N+1、SELECT * や全件取得、不要な FOR UPDATE。index の初期化への組み込み方 |
| B. インフラ・ミドルウェア（午前） | サーバー別 CPU の偏り、構成の分散、nginx（keepalive・静的配信・worker）、MySQL（buffer_pool・flush 設定は永続性への影響も書く）、Go の接続プール、OS の fd・somaxconn。サーバーは ssh で読み取りだけ |
| C. キャッシュ・設計（午後） | JOIN 型 N+1、キャッシュ（キー・無効化・猶予時間・複数 app・初期化）、レスポンス最適化、事前計算・非正規化、非同期化（再起動と最終チェックへの影響）。1 案ごとに PR 2〜3 個の分割案を添える |
| D. 仕様・ベンチ特性 | スコア計算式に直接効く処理、エラー・タイムアウトの原因、ベンチが待たされる処理（ポーリング・retry）、初期化の所要時間、猶予時間でまとめられる箇所。解釈が割れる案は「主催者に質問」に分ける |

## E. 統合（1 セッション）
````text
docs/review/ の結果を統合して docs/backlog.md を更新してほしい（列: ID / 候補 / 視点 / 根拠 / 期待効果 / リスク / 作業量 / 担当 / 状態 / PR）。
- 重複はまとめる。優先度は期待効果 ÷ 作業量で、リスク高は下げる。午前 / 午後 / 保留に分ける
- 担当: すー=<<領域>>、よち=<<領域>>。同じファイルを触る候補は同じ人に寄せる
- 既存の行は消さない。新規は「未着手」
最後に、午前の上位 5 件と午後の上位 3 件、主催者に質問したい点を報告する
````
