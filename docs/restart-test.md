# 追試と再起動試験

- 原文は当日マニュアル「追試」「競技環境の確認」
- 再起動の順序は保証されない（レギュレーション「備考」）

## 主催者の手順と自チームの確認
| # | 主催者が行うこと | 落ちる条件 | 自チームの確認 |
|---:|---|---|---|
| 1 | 4 台とルーターを再起動 | 1 台でも再起動できない | ポータルのサーバリストと AWS コンソールで 4 台の起動を見る |
| 2 | 環境チェック | チェック失敗 | 各台で `sudo /usr/local/bin/envcheck`。終了コード 0 を見る |
| 3 | 複数スタックの確認 | 4 台が同じ VPC に無い | サーバリストの IP と、スタックのリソースの IP を見比べる |
| 4 | 負荷走行 | 3 回とも FAIL または最終スコアの 75% 以下 | 再起動後にポータルからベンチを実行する |
| 5 | 4 台とルーターを再起動 | 1 台でも再起動できない | 手順 1 と同じ |
| 6 | 書き込みデータの確認 | データを取得できない | 下の「データの確認」 |
| 7 | フロントの表示確認 | 表示できない・構造が違う・意図しないデータ | サーバリストの「表示確認用 URL」からログイン、投稿、フィード、画像を見る |

## 再起動前の確認（読み取り）
```sh
# asia1 / europe1 / america1
systemctl is-enabled nginx isureal-go
# asia2
systemctl is-enabled postgresql
```

- 追加したサービスも `is-enabled` で確かめる
- `sysctl -w` や `ALTER SYSTEM` の変更は、設定ファイルと `postgresql.auto.conf` に残っているか見る
- ファイル書き込みやメモリ上の状態を追加したら、再起動後の復元方法を確かめる

## 再起動試験（人の OK を得てから）
1. 全員の作業を止める
2. 4 台を再起動する。順序を変えて、アプリが DB より先に起動しても動くか確かめる
   - AWS コンソールまたは各台の `sudo reboot`
   - 再起動後にサーバリストの IP を見直す
3. 各台で確認する
   ```sh
   sudo /usr/local/bin/envcheck; echo "exit=$?"
   systemctl --failed
   ```
4. ポータルからベンチを実行する。PASS し、直前のスコアの 75% を超えることを見る
5. もう一度 4 台を再起動する
6. データの確認とフロントの表示確認を行う

- 【未確定】ルーターの再起動を選手が行ってよいかは未確認。`docs/regulation.md` の質問を見る

## データの確認
- ベンチ後に新しく書いたデータを、再起動後に読み返す
- 読む先はルーターのみ。サーバリストの「表示確認用 URL」を `ROUTER` に入れる
- 初期ユーザーは当日マニュアル「アプリケーションの表示確認」にある
```sh
. /home/isucon/env.sh
PGPASSWORD="$ISUREAL_DB_PASSWORD" psql -h "$ISUREAL_DB_HOST" -p "$ISUREAL_DB_PORT" \
  -U "$ISUREAL_DB_USER" -d "$ISUREAL_DB_NAME" \
  -c "SELECT max(created_at), count(*) FROM posts;"
curl -sS -o /dev/null -w '%{http_code}\n' -H 'X-Country-Code: JP' "$ROUTER/"
```

- 再起動前後で `posts` の件数と `max(created_at)` が変わらないことを見る
- キャッシュや遅延書き込みを入れたら、その経路のデータも API で読み返す

## 競技終了前の確認
- 最後のベンチが PASS
- 4 台とも起動している
- 4 台とも `envcheck` が成功する
- サーバリストに別スタックが混ざっていない
- 18:00 以降は接続しない
