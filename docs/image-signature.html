画像署名のしくみ

ISUReal（ISUCON2026）/ 2026-10-31 13:40 JST 時点 / asia1 の CPU を食っている正体の説明

TL;DR

画像 URL には「改ざん防止の署名」が付いている。

署名は HMAC-SHA256 を 1000 回連鎖させる重い計算。

レスポンスに画像が並ぶたびに計算していて、asia1 の CPU の 約 55% を使っている。

署名の形式は変えられない。減らせるのは「計算する回数」と「計算する場所」だけ。

暇な europe1 / america1 に計算を任せる案が、いちばん有望。

1. 署名は 2 か所で計算される

作る側は、レスポンスを組み立てるとき。

検証する側は、画像を取りに来たとき。

2. 署名の中身

入力は、画像の持ち主の秘密鍵・exp（期限）・image_id の 3 つだけ。

誰が見ても、同じ画像・同じ exp なら署名は同じ。

HMAC 1 回は SHA-256 のブロック計算が 2 回。1000 回で約 2000 回になる。

3. CPU はどこに消えているか

ベンチ #12618（32326 点）の asia1、CPU プロファイル 60 秒。

割合は「呼び出し先を含む」値。重なるので足し算にならない。

1 回の署名は約 0.4ms と推定（未実測）。60 秒で 9 万回前後になる計算。

4. 今のキャッシュ

  • (持ち主の鍵, image_id) ごとに、発行した URL を 5 分使い回す。
  • 起動時に、新しい投稿 9 万件ぶんの署名を先に作る（ウォームアップ）。
  • asia の投稿は約 62 万件。古い投稿を引く Memories / エクスポートは、ここから外れやすい。
  • ベンチは約 2 分なので、走行中に 5 分の期限が切れることはない。
  • PR #118 で、前の走行が作った分を /api/initialize で捨てる（再起動直後と同じ状態で測るため）。

5. 暇な 2 台に計算を任せる案

europe1 / america1 は CPU 5% で暇。しかも SHA 拡張付きの新しい CPU。

asia1 は SHA 拡張なしの c5。

署名は入力だけで決まるので、別のサーバーで計算しても結果は同じ。

確認済み: 4 台の間は RTT 約 100.8ms。20MB の送信は 2.55 秒（約 8MB/s）。

6. 案の比較

案効果弱点人の判断
A ミス分を europe1 / america1 にまとめて依頼asia1 の署名 CPU を直接減らすミスしたリクエストに +100ms。落ちたら自前計算へ戻す処理が要る不要
B 暇な 2 台が全件（62 万）を先に作って asia1 に送る走行中の計算がほぼ消える。90MB は約 11 秒で送れる計算送った分の期限（5 分）が切れる。再起動直後に間に合わせる設計が要る要判断
C exp を時間の区切りに揃えて使い回す同じ画像の署名が長く使える期限が 24h → 最短 23h に縮む。「期限の形式」を変えたと見られる恐れ要判断
D 投稿時に非同期で署名する新しい投稿だけ速くなる投稿は 60 秒で 231 件だけ。CPU の大半は古い投稿の閲覧不要（効果小）

レギュレーション: 署名と期限の形式・検証結果は変えない（マニュアル「画像URLの検証」）。
